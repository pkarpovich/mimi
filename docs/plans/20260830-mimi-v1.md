# mimi v1 - meeting recorder daemon

## Overview

`mimi` is a macOS daemon in Rust that records meetings without being asked. It watches which
processes hold the microphone, and when one of the known meeting applications takes it, mimi starts
recording two tracks - the user's microphone and the audio the other participants are producing
(captured with a Core Audio process tap) - and writes them to a local folder as one stereo file,
left channel the microphone, right channel everyone else. When the meeting application releases the
microphone, mimi closes the file.

The problem it solves: meetings happen, and nothing keeps a record of them. A transcription pipeline
already exists on this machine (see Context), but nothing feeds it meeting audio. v1 produces the
audio artifact; publishing it into that pipeline is deliberately a later version.

v1 is not "the smallest thing that runs". It is the shape the later versions grow inside, so the
seams below are part of the deliverable even where the implementation behind them is the simplest
one that works.

### Non-goals for v1

Explicitly out of scope. Do not build these, do not leave hooks for them beyond the seams named in
Solution Overview:

- Publishing to NATS (`recordings.completed`) or copying to the NAS. v1 writes to a local folder.
- Transcription, diarization, or any use of the recorded audio.
- Discarding recordings that are too short or silent. Every recording is kept.
- Any UI, menu bar item, notification, or calendar integration.
- Voice processing on the microphone (VPIO / echo cancellation / noise suppression). See Rejected
  alternatives.
- Running on a second Mac, or any multi-machine concern.
- Retention, rotation, deletion, or encryption of recordings.
- Reacting to the microphone being held by anything outside the configured allow-list.

### Rejected alternatives

Each of these was considered and ruled out with evidence. Do not re-introduce them.

- **Two separate files (a mic file and a system file), the way `scosman/Biscotti` does it.** In that
  project the split is a consequence of using VoiceProcessingIO for the microphone: VPIO is a duplex
  AudioUnit that builds its own aggregate device and therefore cannot be a sub-device of the tap's
  aggregate, which forces two engines, two clocks, and an alignment subsystem. mimi does not need
  VPIO (next point), so it does not inherit the split. Measured against it: one aggregate gives
  frame-exact alignment on a shared clock, while the two-engine approach aligns by anchoring on the
  first microphone buffer with a 3-second timeout that silently falls back to no alignment at all,
  and never corrects drift afterwards. That project also merges both tracks back into a single mono
  buffer before transcribing, so the separation it pays for is not used downstream.
- **VoiceProcessingIO on the microphone.** Its purpose is to fix a microphone that is too quiet and
  to suppress the far end bleeding in through speakers. Measured on this machine, inside a live
  Google Meet call on AirPods Pro, the raw microphone track peaked at **-3.4 dBFS** - a healthy
  level, not the degraded one VPIO exists to repair. Meetings here are always on AirPods Pro or
  AirPods Max, never on speakers, so there is no acoustic path from the far end into the microphone.
- **ScreenCaptureKit for system audio.** It requires the broader screen-recording permission; a
  Core Audio process tap is the audio-only API and was verified working (below).
- **A virtual audio device (BlackHole, Loopback).** It rewires the user's audio path. This machine
  already has `Microsoft Teams Audio` (virtual) and Rogue Amoeba's `arkaudiod` in the chain; adding
  another is asking for a conflict.
- **Core Audio property listeners as the activity source in v1.** Polling once a second is simpler,
  already written and verified, and loses at most one second of the opening. Listeners are a later
  swap behind the seam in Solution Overview, not a v1 requirement.
- **Recording on any microphone activation, without an allow-list.** During one night of
  observation `com.apple.CoreSpeech` held the microphone for 37 continuous minutes. Separately,
  opening the microphone forces AirPods into headset mode, which audibly degrades whatever the user
  is listening to - so mimi must not open the microphone speculatively.
- **WAV as the stored format.** Measured at roughly 345 MB per hour. AAC at the same content is an
  order of magnitude smaller.
- **`kAudioAggregateDeviceTapAutoStartKey` set to 1.** Measured: it is a start gate, not a
  convenience. See Context.

Materialized from the `rust-style` skill. These supplement the crate's own conventions.

- **Control flow**: write `for` loops with mutable accumulators instead of iterator combinator
  chains.
- **Early returns**: use `let ... else` to extract values and exit early on failure, keeping the
  happy path unindented.
- **`if let`**: only when the `Some`/`Ok` branch is short and there is no else branch.
- **Naming**: shadow variables through transformations; no `raw_`, `parsed_`, `trimmed_` prefixes.
- **Comments**: do not write them. No inline comments explaining what the code does. A comment is
  justified only when the *why* cannot be recovered from the code - a hidden invariant, a

  repeat it.
- **Doc comments**: a `///` comment belongs on an item another module calls and only when the name

## Context (from discovery)

Everything in this section was measured on this machine (Apple Silicon) with throwaway spikes during
planning, on macOS 26.5.2 and re-checked on 26.6.2. It is not quoted from documentation, and it is
the only surviving record of those probes.

**The Core Audio process tap works here.** A global tap (`CATapDescription` via
`initStereoGlobalTapButExcludeProcesses` with an empty exclusion list) plus a private aggregate
device delivers non-zero PCM: 100% non-zero samples, peak 0.76. The reported bug where the tap
delivers silence while callbacks keep firing did not reproduce.

**Neither a signed binary nor an app bundle is required for the tap.** An ad-hoc signed binary, a
Developer ID signed bundle, and a `launchctl submit` run all captured audio, and no TCC prompt for
audio capture ever appeared. This has not been proven for a real LaunchAgent started at login - see
Post-Completion item 1, which is where that question is settled.

**The exclusion list in `CATapDescription` holds AudioObjectIDs, not PIDs.** Passing a PID produces
`kAudioHardwareBadObjectError` (`!obj`). An empty list taps everything.

**`kAudioAggregateDeviceTapAutoStartKey` is a start gate.** Measured directly, twice: with the key
set to 1 and an aggregate whose only source is the tap, **no buffer ever arrives** while nothing is
playing - `AudioDeviceStart` returns 0 immediately and the IOProc never fires. With the key set to 0
and the same composition, the first buffer arrives after 55 ms. With the key set to 1 but a
microphone sub-device present, buffers arrive after 105 ms because the microphone drives the device.
So the flag makes capture depend on somebody else producing audio first. **v1 sets it to 0.**

**Buffer layout depends on the aggregate's composition.** With only the tap, the IOProc delivers
`mNumberBuffers = 1`, a single 2-channel buffer. With a microphone sub-device added, it delivers
`mNumberBuffers = 2`: buffer 0 is the microphone (1 channel), buffer 1 is the tap (2 channels), same
frame count (512 frames each, measured). The default *output* device sits in the composition as the
main sub-device and contributes **no** buffer, because it has no input streams. Reading channels
*within* a buffer instead of treating each buffer as a track produces a file where the two sources
are concatenated rather than separated - this mistake was made once already during the spike.

**The delivered sample rate comes from the aggregate device, not from the tap.**
`kAudioTapPropertyFormat` reports 48000 Hz regardless: on AirPods Pro, where the stream is really
24000 Hz, it still says 48000, which is what makes a file written from it play at double speed.
`kAudioDevicePropertyNominalSampleRate` **read on the aggregate device** reported 48000 Hz on the
built-in devices and matched the rate measured by counting delivered frames over wall-clock time.
That property is the source of truth for the client format. Measured values: 24000 Hz on AirPods Pro
in headset mode, 48000 Hz on the built-in speakers and microphone.

**Sample rate is not a constant and must not be read once.** It changes mid-stream when the default
device changes, and it also changes when a device switches mode without changing identity - opening
the microphone forces AirPods into headset mode, same UID, different rate.

**Changing the default audio device mid-recording silently kills the capture.** Measured: the
aggregate was built while AirPods Pro were default; when the default moved to the built-in devices
at second 14, the IOProc kept firing (its rate even doubled, 50 to 100 buffers per second), but the
data became first duplicated across both tracks and then entirely zero for the remaining 40% of the
recording. Callbacks alive, counters healthy, file silent.

**Input and output UIDs are distinct even for one physical device.** AirPods Pro appear as
`20-F4-D4-60-E4-29:output` and `20-F4-D4-60-E4-29:input` - two different UID strings sharing a MAC
prefix. The built-ins are `BuiltInSpeakerDevice` and `BuiltInMicrophoneDevice`. So the aggregate's
main sub-device and its microphone sub-device never collide, and no de-duplication is needed. A
composition that does repeat one UID (tested deliberately) produces no microphone buffer at all.

**Microphone level is fine without voice processing.** Inside a live Meet call on AirPods Pro the
microphone track peaked at -3.4 dBFS.

**Recording does not steal the microphone from the meeting.** The spike held the input at the same
time as the browser; Core Audio grants the input to several clients at once.

**On this machine Google Meet runs in Dia, and the process that holds the microphone is
`company.thebrowser.browser.helper`** - the Arc-era bundle id, not `company.thebrowser.dia`. An
allow-list containing only the main bundle id would never have matched. Teams appears as five
processes (`com.microsoft.teams2`, `.modulehost`, `.helper` x3, `.notificationcenter`), Slack as
three. Matching must be by bundle-id prefix, and the list must live in configuration, not in code.

**mimi will see itself** in the process list once it opens the microphone and must exclude its own
process.

**The audio devices present on this machine** include AirPods Pro #4, AirPods Max #2, a RØDE NT-USB+,
two DELL monitors, the built-in speakers and microphone, `Microsoft Teams Audio` (virtual) and Rogue
Amoeba's `arkaudiod`. Device changes are routine, not exceptional.

**`ExtAudioFile` is AudioToolbox, not CoreAudio.** `objc2-core-audio` does not carry it. The binding
is `objc2-audio-toolbox` 0.3.2, feature `ExtendedAudioFile` (verified resolvable). Everything else
the plan uses - `CATapDescription`, `AudioHardwareCreateProcessTap`,
`AudioHardwareCreateAggregateDevice`, `AudioDeviceCreateIOProcIDWithBlock` and every aggregate key
below - is present in `objc2-core-audio` 0.3.2.

**A transcription pipeline already exists on this machine** and is the eventual consumer, though not
in v1: a NATS stream `recordings` carries `recordings.completed` messages shaped
`{id, source, channel, title, started_at, ended_at, duration_seconds, file: {storage, path},
transcribe, language}`, consumed by a durable consumer that transcribes and republishes
`recordings.transcribed`. The single-file shape of that contract is one reason v1 produces one file.

**The reference implementation** consulted during planning is `github.com/scosman/Biscotti` (Swift, a
meeting recorder by a former Apple engineer). Everything mimi needs from it is written down in this
plan; it is a pointer for orientation, never a specification to match.

## Solution Overview

### The four seams

v1 is shaped by four seams, because each is a place a later version will need to change without
touching anything above it.

1. **The activity source is an interface, its polling is an implementation.** Something answers
   "which processes hold the microphone right now". Behind it in v1 is a one-second poll; Core Audio
   property listeners replace it later with no change above. The allow-list lives in configuration
   because discovery proved it wrong on first contact and it will keep going stale.

2. **Capture is two tracks, always.** Microphone and system audio are separate concepts from the
   IOProc all the way to the writer - the ring carries them apart, and they are only combined at the
   moment of writing. This is what lets a later version put voice processing on the microphone
   alone, or give each track its own rate, without a rewrite.

3. **What was recorded and what happens to it are different layers.** A finished session is handed
   to a sink. In v1 the only sink writes to a local folder; the NAS-plus-NATS sink is a second
   implementation later, not a rewrite.

4. **One stereo file is the writer's decision, not capture's.** Capture always yields two tracks;
   folding them into left and right happens in exactly one place, `src/writer.rs`.

### How recording behaves

A session starts when a process whose bundle id matches the allow-list takes the microphone, and
ends when no such process holds it any more - with a grace period, so a meeting app that briefly
drops and re-takes the input does not split one meeting into two files.

The file is ADTS AAC, stereo, at a fixed sample rate chosen by configuration. Left is the
microphone, right is everyone else. The container matters: ADTS frames are self-synchronising and
carry no index, so a file left behind by a crash or a `kill -9` is still playable up to the point it
stopped, which a daemon-written file must survive. That guarantee only holds if the file is written
where it will finally live, so recording writes directly into `output_dir` under a `.partial`
suffix and is renamed on completion - never into a temporary directory.

Because the delivered sample rate is not stable, the file's rate is fixed and the incoming stream is
converted to it. `ExtAudioFile` performs that conversion when the client format differs from the
file format. The client format itself is set once and cannot be changed while the file stays open,
so a later change in the delivered rate is resampled onto it - see Sample rate handling.

When the default input or output device changes, or when the delivered rate changes without the
devices changing, capture is rebuilt **without closing the file** - the recording continues into the
same artifact and the gap is limited to the hardware settling time. This is a v1 requirement, not a
refinement: discovery showed that without it the recording silently becomes digital silence.

Silence is watched for, because the failure mode is invisible: the first seconds after a start and
after every rebuild are checked for all-zero samples, and an all-zero window is logged loudly and
recorded in the sidecar.

## Technical Details

### Configuration

`$HOME/.config/mimi/config.toml`, TOML, read once at startup. Fields, with defaults:

- `output_dir` (string, default `$HOME/Recordings/mimi`) - where recordings are written, including
  while still in progress.
- `meeting_bundle_prefixes` (array of strings) - a process matches when its bundle id starts with
  any entry. Default: `company.thebrowser.`, `us.zoom.`, `com.microsoft.teams2`,
  `com.tinyspeck.slackmacgap`, `com.google.Chrome`.
- `sample_rate` (integer, default `24000`) - the fixed rate of the written file.
- `bit_rate` (integer, default `96000`) - AAC bit rate.
- `stop_grace_seconds` (integer, default `15`) - how long the microphone must stay released before a
  session is closed.
- `poll_interval_ms` (integer, default `1000`) - activity source polling period.

A missing file is not an error: defaults apply. A malformed file is a startup error - the daemon
exits rather than recording with a silently wrong allow-list.

### Artifacts

For a session that started at 2026-08-30 14:32:05 local time in Dia (matched by the prefix
`company.thebrowser.`, so the label is `thebrowser`):

- `2026-08-30T14-32-05-thebrowser.aac.partial` while recording, renamed to
  `2026-08-30T14-32-05-thebrowser.aac` when the session ends.
- `2026-08-30T14-32-05-thebrowser.json` - a sidecar written at completion, carrying `started_at`,
  `ended_at`, `duration_seconds`, `bundle_id`, `sample_rate`, `channels`, `device_changes` (how many
  rebuilds happened) and `silent` (whether the silence check ever fired). The sidecar exists because
  a later version needs exactly these fields to build a `recordings.completed` message, and because
  a file that turned out silent must say so somewhere.

The label comes from the matched allow-list prefix, lowercased, trailing dot removed, then reduced to
its last dotted component: `company.thebrowser.` -> `thebrowser`, `us.zoom.` -> `zoom`,
`com.microsoft.teams2` -> `teams2`, `com.tinyspeck.slackmacgap` -> `slackmacgap`,
`com.google.Chrome` -> `chrome`.

### The aggregate device

`AudioHardwareCreateAggregateDevice` takes a `CFDictionary`. These are the literal keys, captured
from the working spike (the constants resolve to exactly these strings):

| key constant | literal | value |
|---|---|---|
| `kAudioAggregateDeviceNameKey` | `name` | any display name |
| `kAudioAggregateDeviceUIDKey` | `uid` | a stable UID owned by mimi |
| `kAudioAggregateDeviceMainSubDeviceKey` | `master` | the default **output** device's UID |
| `kAudioAggregateDeviceIsPrivateKey` | `private` | 1 |
| `kAudioAggregateDeviceTapAutoStartKey` | `tapautostart` | **0** - see Context |
| `kAudioAggregateDeviceSubDeviceListKey` | `subdevices` | array of dictionaries |
| `kAudioAggregateDeviceTapListKey` | `taps` | array of dictionaries |

A sub-device entry is a dictionary, not a bare UID: `{kAudioSubDeviceUIDKey ("uid"): <device uid>}`,
plus `{kAudioSubDeviceDriftCompensationKey ("drift"): 1}` on the microphone entry. A tap entry is
likewise a dictionary: `{kAudioSubTapUIDKey ("uid"): <the CATapDescription's UUID string>}` - an
array of bare UUID strings is accepted by the API and yields a tap that contributes nothing.

The sub-device list holds the default output device and the default input device. Their UIDs are
always distinct (Context), so no de-duplication is required; if a future device ever reports the same
UID for both, include it once.

Teardown order, on both the normal stop path and every rebuild: `AudioDeviceStop`, then
`AudioDeviceDestroyIOProcID`, then `AudioHardwareDestroyAggregateDevice`, then
`AudioHardwareDestroyProcessTap`. One helper owns this sequence and both paths call it.

### Sample rate handling

The delivered rate is read from `kAudioDevicePropertyNominalSampleRate` **on the aggregate device**,
after the aggregate is created. `kAudioTapPropertyFormat` is never used for this - it reports 48000
Hz even when the stream is 24000 Hz (Context). The rate is read again after every rebuild, and it is
also re-read on each poll tick so that a mode change on an unchanged device is noticed.

The file is created once at `config.sample_rate`. The client format carries the delivered rate of the
first block written and cannot be changed afterwards (measured in Task 10: `ExtAudioFile` answers
`kExtAudioFileError_InvalidOperationOrder` and every later write fails), so frames captured at a
different rate after a rebuild are resampled onto the established client rate instead.

### The ring and its block contract

The IOProc hands the writer thread blocks through a preallocated ring. A block carries, per the
two-track seam:

- the microphone frames for this callback (may be empty when the microphone track is absent),
- the system frames for this callback,
- the frame count,
- the host time of the block,
- the **format generation** - a counter incremented on every client-format change.

The generation is what makes a rate change safe: the writer sets the client format from the block it
is about to write, so frames captured at the old rate are still written at the old rate, and no
drain-before-reconfigure handshake is needed. Without it, blocks queued at 24000 Hz would be
converted as if they were 48000 Hz at the moment the default device changes - an audible glitch at
exactly the point the acceptance scenario exercises.

The `ExtAudioFile` handle is owned solely by the writer thread. Nothing else calls into it; the
rebuild path reaches the writer only by pushing blocks with a new generation.

### AAC bit rate

Setting the encoder bit rate on an `ExtAudioFile` is a three-step sequence and the order matters:
set the client format first (that is what instantiates the codec), then read the converter out with
`kExtAudioFileProperty_AudioConverter` and set `kAudioConverterEncodeBitRate` on it, then commit by
setting `kExtAudioFileProperty_ConverterConfig` to a **pointer-sized NULL**. Skipping the commit
makes the bit rate setting silently do nothing; passing a `UInt32` zero instead of a null pointer
crashes the writer thread.

### Real-time discipline

The IOProc runs on a real-time thread. It must not allocate, lock, block, or touch the filesystem:
it interprets the buffer list, copies both tracks into the preallocated ring, and returns. A separate
writer thread drains the ring, performs the stereo fold, the encode and the write. Errors from the
writer thread are surfaced through a shared slot and read after the thread joins.

### Acceptance scenario

The scenario every verification aims at, because it is the one that actually happens: **Pavel joins a
Google Meet call in Dia wearing AirPods Pro, talks for several minutes, and at some point the AirPods
die and he switches to AirPods Max mid-call.** Afterwards there is exactly one file in the output
folder, it plays for the full duration of the call at the correct speed, his voice is on the left
channel and the other participants on the right, and the recording continues across the device
switch instead of turning to silence.
